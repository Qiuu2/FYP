# R4 双人复核：怎么查

> 铁律 R4：每个数据模块由**非采集者**抽 5% 数据点对照源核对，并在 commit message 写「R4复核：<姓名>」。
> 本轮分工：采集人 **賈贇**，复核人 **陈于嘉**。

## 零、先说清楚：R4 不是跑 `manifest.py verify`

这两件事经常被混为一谈，但它们证明的东西完全不同：

| | `manifest.py verify` | R4 复核 |
|---|---|---|
| 谁做 | 谁都行，机器跑 | **必须是非采集者** |
| 查什么 | 文件哈希对不对得上 manifest、必填字段有没有缺、请求日志在不在 | **数字本身是不是真的** |
| 能证明 | 文件入库后没被人改过、格式完整 | 数字确实来自它声称的那个源 |
| 证明不了 | **数字对不对** | — |

`verify` 是自动化的完整性检查，采集脚本自己就会让它通过——它读的是我们自己写的 manifest，
拿我们自己写的哈希去对我们自己产出的文件。**一份数字全错但格式规整的 CSV 照样能 verify 全绿。**

R4 要的是**离开这个自洽的小世界，回到源头去问一遍**：点开请求 URL，看接口现在返回什么，
跟 CSV 里那一行对不对得上。这件事机器替不了，同一个人做也没意义——
采集者按同样的理解再查一遍，只会重复同样的误解。所以铁律写死了必须换人。

## 一、先搞清楚点哪个链接

manifest 里有两个跟 URL 有关的字段，用途不同：

| 字段 | 是什么 | 拿它干什么 |
|---|---|---|
| `source_url` | 数据源的**端点**或官方页面 | 说明数据来自哪个机构/接口，**不保证能直接点开看到我们那一行** |
| `request_log` | 同目录下的 `.requests.tsv`，逐行记录**能复现每一行数值的完整请求 URL** | **复核就点这里面的 URL** |

2026-08-26 之前采集的几份，manifest 只有端点没有请求日志——点开
`https://api.openalex.org/works` 是端点说明、点 `clinicaltrials.gov/api/v2/studies`
返回全库 JSON、`.../institutions/ror:{ror}` 里的模板变量没被替换会直接 404。
这些已经用 `scripts/rebuild_request_urls.py` 回填了逐行 URL，
`manifest.py verify` 现在也会拦住这类问题。

## 二、抽样怎么抽

按 5% 算，7 份 API 数据约 620 个数据点 → 抽 **31 个点**。建议每份文件按行数比例分配，
每份内部随机取行（别只取头几行，头部往往是最早的年份，最容易对）。

```python
# 在 data_repo/ 下跑，生成一份可复现的抽样清单（种子固定，别人能复算）
import csv, random, pathlib
random.seed(20260826)          # 换人复核时换种子，并把种子写进 commit message
for f in sorted(pathlib.Path("raw").glob("*.csv")):
    rows = list(csv.DictReader(open(f, encoding="utf-8-sig")))
    k = max(1, round(len(rows) * 0.05))
    for r in random.sample(rows, k):
        print(f.name, r)
```

## 三、一个点怎么核

以 `openalex_papers_by_quarter.csv` 里 `ai,hk,2015Q1,93` 这一行为例：

1. 打开 `manifests/openalex_papers_by_quarter.csv.requests.tsv`
2. 找 `row_key` 等于 `ai/hk/2015Q1` 的那一行，复制它的 `request_url`
3. 浏览器打开，看返回 JSON 里的 `meta.count`
4. `meta.count` 应该等于 CSV 里的 `93`

对得上就打勾；对不上**先别改数据**，把行键、URL、你看到的数字一起发出来。

几点注意：

- **OpenAlex 的计数会随时间上涨**。索引在持续回填，隔几个月复核同一个 URL，
  数字可能比当初采集时略高（0.1%–2%，年份越新差得越多）。
  差在这个量级内属正常，记一句「复核日期＋实测值」即可；差一个数量级才是问题。
- `request_url` 里**故意不带 api_key 和 mailto**——密钥不入库，mailto 不影响返回计数。
  不带 key 也能查，只是限速严一点。
- `covers_rows` 那列写 11 的（如 institutions、shares），表示这一个请求一次返回了
  11 行数据，核的时候对照返回里对应年份那一项。

## 四、人工采集的那几份（p2–p6）——先看 sources，别只看 source_url

**2026-08-26 第一轮复核踩过的坑，先说明白。** 这五份都是**多源人工采集**，
但 manifest 的 schema 原来只有一个 `source_url` 字段，等于把几十个来源压成了一个链接。
复核者点开那一个链接，自然只能核到一部分，于是误判成"数据对不上"。

现在每份 manifest 都加了 `sources` 数组，列出 raw 文件里出现过的**全部** URL，
以及每个被多少行引用、出现在哪个小节。复核**以 sources 和 raw 文件里的逐行 URL 为准**。

第一轮那三条反馈，逐条说明：

| 反馈 | 实际情况 |
|---|---|
| **p3**「仅核对官方表 14 家，其余页面上未见」 | 判断没错。`source_url` 指的是港交所 18C 官方页（SRC2），它**本来就只有 14 家 18C 公司**。18A 那 84 家来自 SRC1（头豹研报 PDF）＋几十条逐家的媒体/律所链接，raw 文件的 `=== SERIES: listings_18a_by_year ===` 段落写明了逐年的直接来源。现在 12 个来源都在 sources 里了。 |
| **p4**「页面与 raw 文件中名称不一致」 | 两层原因。① `source_url` 是 SFC 的虚拟资产平台名册，只覆盖 13 家 VATP；8 家虚拟银行和 16 张 SVF 牌照各自来自 info.gov.hk 的独立新闻稿。② 名称差异是**已知并已记录**的：raw 文件 NOTES 里写着「发牌名→现名官方映射 NOT_FOUND（HKMA 站不可达），学生本地补」——SFC/HKMA 页面显示的是**现名**，我们记的是**发牌当时的名称**。另外 `clean/fintech_license_events.csv` **每一行都带自己的 source_url**，逐条点开即可核对。 |
| **p6**「仅有岭南大学，work_count 未按年份显示」 | 判断没错。`source_url` 是岭南那一条的 ROR 解析查询，它只解析机构标识，**不含任何逐年产出数**。逐年 works_count 来自 OpenAlex 的机构端点。**要核这部分，不要用 p6，去用 `openalex_institutions_counts.csv`**——那份是这批数据的权威版本，配套的 `.requests.tsv` 里 11 个机构的请求 URL 一应俱全（含岭南、应科院、浸会、教大），点开就能看到 `counts_by_year`。 |

### 怎么核 p2–p6

1. 打开 manifest，看 `sources` 数组，找到覆盖你要核那一行的那个 URL
2. p2 / p4 / p5 的 raw 文件里，**每一行数据都自带 `source_url` 列**——直接用那个，最准
3. p3 用 SRC1/SRC2/SRC3 宏，raw 文件开头有对照表
4. 核不到的时候先确认：这一行的来源是不是根本就不是 `source_url` 那一个

如果某一行在它自己声明的来源里也找不到，那才是真问题，按第五节报告。



这几份的 `source_url` 本来就是官方页面或带完整查询串的接口地址，直接点开即可。
它们是人工从政府统计处、HKEX、SFC、InvestHK 等页面整理的，
复核方式是打开页面找到对应数字，跟 `raw/` 里的文本记录比对。
